# ChainInquest V3

## 项目调查 / Project investigation

ChainInquest accepts a user-vetted project manifest and an explicit scope. The workflow pins the range, confirms contract bytecode at the ending block, queries each confirmed address using the existing investigation engine, and recomputes a deduplicated project report. A source link records the curator's attribution evidence. Bytecode confirms an address has code at the snapshot. It does not establish ownership or an exact deployment date.

Run from the repository root:

```sh
MONAD_TESTNET_RPC=https://testnet-rpc.monad.xyz python3 skills/onchain-address-inspector/scripts/v3.py --input examples/circle-monad.json
```

The input is a JSON object with `goal` (overview, activity or flows), `scope` (recent_blocks, start_block/end_block pair, or days 7/30), `budget_seconds` (15–240), and `manifest`. Use the [project manifest rules](../skills/onchain-address-inspector/references/project.md) without `report_file`. V3 accepts unknown deployment blocks and dates and preserves them as null. It requires the curator to confirm each included contract and provide an HTTPS source. A job has at most eight entries and a fixed block window at most 32 blocks.

The output includes the investigation ID, the chain report, evidence and coverage. State and checkpoints live in `artifacts/investigations/` by default. On Linux or macOS, resume with the same store and `--resume INVESTIGATION_ID`. A resume reuses completed address checkpoints and the original scope. Interrupted or partial jobs can be run again up to three attempts. Exit 2 indicates a partial or failed investigation.

Live checkpoint: the Circle Monad example completed on public QuickNode for blocks 81751912–81751915. Both addresses had code at the shared ending block. No matching top-level transactions or events were returned within those four blocks. This validates live scope and project aggregation for that sample. See the [documented contract registry](https://developers.circle.com/cctp/references/contract-addresses) and [USDC addresses](https://developers.circle.com/stablecoins/usdc-contract-addresses).

## Networks and providers

The V3 runner takes an explicit chain ID from the manifest. Supported profiles are Monad Testnet 10143, Base Mainnet 8453, and Ethereum Mainnet 1. The endpoint comes from the operator's environment or the built-in public profile. Overrides are `MONAD_TESTNET_RPC`, `CHAININQUEST_BASE_RPC`, and `CHAININQUEST_ETHEREUM_RPC`. RPC identity is checked before collecting. Multi-chain jobs use recent blocks per chain or the same absolute UTC time interval. Explicit heights belong to one chain. Native amounts and addresses stay chain-scoped and are never summed across chains.

For 7/30 days, Etherscan V2 `ETHERSCAN_API_KEY` may supply top-level transaction candidates for the selected chain. Each candidate is checked against RPC. The index does not attest an indexed-through height, so candidate retrieval does not establish complete history. Events use bounded RPC log filters and receipt checks. Internal calls and traces are outside this scope. A limited public endpoint may return partial results from any chain. No provider credit or historical completeness is inferred from a successful chain ID check.

Use `examples/circle-multichain.json` for the three-network project. The fixed public endpoints and index are read only. Refer to the [Base RPC documentation](https://docs.base.org/base-chain/api-reference/ethereum-json-rpc-api/eth_chainId) and [Etherscan supported chains](https://docs.etherscan.io/supported-chains).

## Evidence graph and analysis

Each report carries chain-scoped projects, deployments, contract and address nodes, transactions, events and evidence records. Graph facts reference validated transaction or log evidence. Project attribution stays in a separate curator-supplied collection. Native value flow edges require successful receipts. ERC-20 transfer edges represent emitted logs rather than independently reconstructed balance changes. Approvals are counted as approvals and do not create fund flow edges.

Daily buckets use UTC. Positive counts in partial data describe observed evidence, and unobserved days or metrics are null. The first-observed and repeat counts describe counterparties within the returned sample. Deterministic candidates cover strong direct-initiator concentration and increases between fully covered adjacent UTC days. Candidate records include the underlying evidence references.

For optional secondary-provider corroboration, append `_SECONDARY` to a chain's environment variable. The runner compares the ending block and samples at most two transaction receipts and two event receipts, within the job budget. A disagreement marks chain coverage partial and suppresses graph analysis. Missing secondary data retains the primary report with explicit corroboration status. Recompute and validate a saved report with `python3 scripts/verify_evidence.py FILE.json`.
